# ADR-0071: Ключ API між HA і Велешею; пам'ять із Telegram — лише особиста

- **Status**: accepted
- **Date**: 2026-10-03

## Контекст

Розбір можливих обходів захисту перед керуванням з Telegram (ADR-0070):

- `/v1/chat/completions` без автентифікації (режим ADR-0035 без
  `VELESHA_USERS`): будь-хто в локальній мережі мав повне керування, а з
  ADR-0069 ще й міг вписати мітку `Velesha-User: punka-mobile` і читати
  особисту пам'ять. Read-only у Telegram від цього не захищає.
- Автонавчання пам'яті з Telegram: переслане чуже повідомлення («Еббі
  можна курятину») могло стати спільним фактом і впливати на відповіді в
  HA для всіх.

## Рішення

- `VELESHA_API_KEY` (секрет у `api/secrets.enc.env`): коли заданий,
  `/v1/chat/completions` і `/v1/models` вимагають `Authorization: Bearer
  <ключ>` (`secrets.compare_digest`), інакше 401. Той самий ключ — у
  записі `llama_cpp` в HA. Мітці пристрою довіряємо лише за правильного
  ключа. Поки ключ не заданий — поведінка як раніше (поетапне
  ввімкнення без простою). `/webhook` — зі своїм токеном (ADR-0061).
- Telegram: з пересланих повідомлень (`forward_origin`) пам'ять не
  вчиться; з власних — факти лише в особисту пам'ять.

## Наслідки

- Тести через curl тепер потребують ключа.
- Веб-пошук як можливий канал витоку і відсутність обмеження частоти —
  відомі, не закриті (низький ризик при одному дозволеному користувачі).
