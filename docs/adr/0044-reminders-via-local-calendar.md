# ADR-0044: Разові нагадування через HA Local Calendar

## Контекст
«Нагадай купи молока о 19» — потрібне пуш-сповіщення на телефон у заданий час.
Нотатки Obsidian тут не потрібні (з'ясовано в розмові): досить банального
разового нагадування з текстом і часом. У HA вже є `notify.mobile_app_punkas26`
(HA Companion зареєстрував сам). Автоматизацій через API не створити
(`/api/config/automation/config` → 404, ADR-0041), а `local_calendar` можна
додати програмно через `config_entries/flow` (та сама схема API, що для timer-
helper'ів у ADR-0041) — так і зроблено: створено `calendar.nagaduvannia`.

## Рішення
- `remind_me(text, time?|in_minutes, date?)` і `get_reminders()` у `tools.py`.
  Час рахується в коді (`_parse_clock`, `_parse_day`): голий "о 19", що вже
  минув сьогодні, автоматично зсувається на завтра. Пише подію через сервіс
  `calendar.create_event` (`start_date_time`/`end_date_time`, +1 хв), результат
  перевіряється зчитуванням календаря назад — жодної заяви про успіх без
  підтвердження.
- **Один календар на користувача**, не спільний: `_reminder_calendar_for(user)`.
  Для `default` (однокористувацький режим, ADR-0035) — вже створений
  `calendar.nagaduvannia`. Для будь-якого іншого імені — авто-створення через
  `config_entries/flow` при першому зверненні; мапа користувач→календар
  кешується в `api/data/reminder_calendars.json`, ідемпотентно (спершу шукає
  календар з такою назвою серед сутностей, лише тоді створює новий — інакше
  повторний виклик після збою міг би плодити дублікати; справжній entity_id
  береться діфом станів до/після, а не вгадуванням транслітерації HA).
- **Скасування** (`cancel_reminder`, ADR-0044 update): шукає серед активних подій
  користувача за частиною тексту; кілька збігів — перепитує, жодного — каже. HA не
  має сервісу `calendar.delete_event` (лише `create_event`/`get_events`), видалення
  працює через WebSocket-команду фронтенду `calendar/event/delete` (`ha_client.delete_calendar_event`),
  результат перевіряється повторним читанням. Оновлення нагадування окремим
  інструментом не робили — це «скасуй + постав нове» через наявні два інструменти.
- **Сповіщення — окремо, HA-стороною**, як і вимкнення телевізора (ADR-0041):
  одна автоматизація `docs/ha/reminder-notify-automation.yaml` на подію
  `calendar.event start`, шаблон `trigger.entity_id → notify.<пристрій>` вибирає
  сервіс сповіщення. Новий користувач = новий рядок у trigger і в мапі; агент
  сам підказує, який рядок додати, коли вперше створює для когось календар.
  Наше API ніколи не викликає `notify.*` само.
- Гейт: `_REMIND_RE` ("нагад…"), як усі дії.

## Наслідки
- Перевірено на реальному HA: створення для `default` і для тестового
  «olha» (авто-провіжн, ідемпотентність підтверджена — другий виклик не
  створив дубль), видалення подій (сервіс `delete_event` не існує;
  working шлях — WebSocket `calendar/event/delete`, використано лише для
  прибирання тестових даних, у продуктовому коді не потрібен: нагадування
  одноразові й самі не видаляються після спрацювання, залишаються в
  календарі як минула подія — прибирання старих подій не реалізовано).
- Доки нову людину не додано в `docs/ha/reminder-notify-automation.yaml`,
  її нагадування створюються, але сповіщення не приходить — агент про
  це попереджає в тексті відповіді при першому створенні.
- Без `VELESHA_USERS` (ADR-0035) усі — `default`, один спільний календар.
